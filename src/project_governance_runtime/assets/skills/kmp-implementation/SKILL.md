# KMP Implementation

Use this router when the selected target-owned route explicitly enables Kotlin Multiplatform work.
Treat the selected packet as the leaf authority; do not maintain or infer a second leaf list here.

## Establish the project shape

Before editing, confirm the explicit facts that can change the design:

- target families and runtime profiles, including every supported or conditional target;
- source, binary, and device support tiers;
- artifact forms and external consumers;
- shared, native, or mixed UI posture;
- standalone, companion, or intermittently connected device topology; and
- platform API, lifecycle, concurrency, event-delivery, power, and interop pressure.

If a material fact is missing, say which decision it blocks. Never substitute an Android-phone
default for an undeclared Apple, JVM, web, native, server, or wearable target.

## Route the decision

Keep four identities separate: compilation target, source set, runtime/device profile, and artifact
consumer. Start from the target repository's existing module and source-set topology, then use the
automatically selected leaves in the context packet. Apply target governance and local evidence
before generic examples.

For bridge work, first locate the shared policy owner and the thin platform transport. Keep
high-cadence data and ordering inside the narrowest native or KMP boundary that can process it;
cross language or process boundaries with bounded commands, state, results, and diagnostics.

For wearable work, explicitly decide authority during disconnect, reconnection, backgrounding, and
partial sensor availability. Phone-like lifecycle, continuous connectivity, and phone-owned
execution are hypotheses, not defaults.

## Maintain enabled surface validation

For KMP-backed UI, binding, host, or renderer work, run
`project-governance plan --pack kmp-surface-validation --json`. An unknown or inactive pack means
the optional capability is not enabled; do not create configuration on its behalf.

When the pack is active, read `config/validation/kmp-surfaces.yaml` and its `target_catalog` before
editing. Route platform-exclusive behavior to platform-owned validation. For a cross-surface
capability, update the existing area or add one, preserve a target route for every catalog target,
and split host surfaces that can break, ship, or be validated independently. Keep broad routing
shallow; use guarded roles and claims only for a fragile seam. Finish with
`project-governance check --pack kmp-surface-validation`.

## Completion evidence

Report the declared project shape, source-set and artifact decisions, selected skills, active
surface-graph impact, exclusions or missing facts, target-owned validation commands, and any target
or device claim that remains unproved. Do not claim whole-of-KMP safety from one Android build or one
simulator run.
