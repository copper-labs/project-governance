# KMP Skill V0 Evaluation

## Decision

Recommend promoting the stable `kmp-implementation` router and six V0 leaves as one governed KMP
core during a separately authorized cutover. Do not publish a wheel or update an adopter from this
evaluation alone.

The final frozen comparison covered five project shapes in three modes: no skill, explicitly forced
guidance, and automatic routing. Codex and Claude received the same task facts, canonical skill
bodies, and required progressive-disclosure references. Automatic routing tied or improved on
forced guidance and improved at least one material decision or restraint over the no-skill baseline
for every V0 capability. No final automatic result contained a blocking target assumption.

## Scenario Outcomes

| Scenario | Automatic composition | Material improvement over baseline | Result |
| --- | --- | --- | --- |
| Shared domain placement | Router + source-set boundary | Required the real compilation graph, narrowest honest source set, complete target implementations, and an explicit interface-versus-expect/actual decision. | Pass |
| Target matrix upgrade | Router + build/compatibility | Treated compatibility as one cited matrix while preserving every dimension not forced to move and requiring per-target artifact and consumer proof. | Pass |
| Native event stream | Router + concurrency + API/artifact | Added generation-based stale-callback rejection, bounded event semantics, thin Swift transport, and reentrancy-safe teardown. | Pass |
| Published framework API | Router + API/artifact | Distinguished Kotlin source from the generated consumer contract and blocked export technology, distribution form, and architecture choices until declared. | Pass |
| Wearable companion reconnect | Router + sharing/architecture + concurrency + test/evidence | Refused both phone-owned and watch-owned authority defaults, separated state/events/results, bounded bridge pressure, and required distinct Wear OS/watchOS proof. | Pass |

The scenarios cover all six leaves. The router adds project-shape, missing-fact, target-tier,
artifact-consumer, and device-topology constraints to each automatic packet without creating a
second capability list.

## 2.2.0 Focused Re-Evaluation

KMP Surface Validation changes only the selected router and test/evidence leaf. The unchanged five
leaf bodies, six decision guides, manifest matchers, original five-scenario fixture, and V0 rubric
retain their 2026-08-24 result.

Two affected behaviors were re-evaluated on 2026-08-30:

- an implementation-shaped shared UI task materializes `kmp-implementation`, discovers the optional
  pack through the existing planner, preserves platform-exclusive ownership, and requires every
  catalog target when the pack is active; and
- a proof-shaped parity task automatically composes `kmp-test-and-evidence`, keeps
  `required_target_proof_claims` target-local, records missing proof as blocking, and runs the same
  existing pack command after graph maintenance.

Focused selection, exact materialization, source-versus-installed byte identity, bounded packet, and
surface-validator fixtures passed. The revised bodies remain provider-neutral and add no target
inventory, automatic activation, proof runner, or product-specific path. Their body digests above
replace only the two invalidated entries in the frozen record.

## Corrections Made During Evaluation

The first diagnostic run omitted required decision-guide bytes and therefore was not a valid
promotion comparison. The final packet included those exact references. Before freezing the final
candidate, three narrow instruction gaps were corrected:

- sharing guidance now forbids inferring watch authority, offline durability, queues, or replay;
- compatibility guidance now preserves every matrix dimension not forced to move and rejects a
  universal upgrade or commit sequence; and
- concurrency guidance now forbids reentrant teardown from joining the callback that invoked it.

All affected deterministic selection and static-contract tests passed after these corrections.

## Residual Risks

- These are controlled synthetic architecture scenarios, not compiling consumer fixtures.
- One frozen provider run per scenario and mode demonstrates decision value but does not eliminate
  stochastic model variation.
- Detailed platform APIs, distribution mechanics, data/offline architecture, UI frameworks, and
  wearable implementation mechanics remain deliberately deferred overlays.
- Real consumer builds and physical Wear OS/watchOS proof remain required before making adopter,
  artifact, performance, background, power, or device-support claims.

Any change to a selected skill, required reference, scenario, rubric, matcher, or canonical packet
invalidates the affected part of this record.
